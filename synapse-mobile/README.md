# Synapse mobile

Expo SDK 57 app for `https://www.fuseon.in`, with a native WebView, push notifications,
offline saved-page reading, pull-to-refresh, Android back navigation, external
browser links, branded splash screen and app icons. Expo Router starts at
`src/app/index.tsx`; the older screen components are retained but are not the app
entry point.

## Run and build

```powershell
npm ci
Copy-Item .env.example .env.local
npx expo start
```

`EXPO_PUBLIC_SITE_URL` must be the HTTPS origin of the deployed website. To change
the site, set it before building. The live site's apex and `www` redirects are
both handled inside the app. The Expo web target is an informational launch
page; the WebView and native features run on Android and iOS.

There is no EAS project linked yet. Before making an installed push-enabled build:

1. Sign in to an Expo account with `npx eas-cli@latest login`.
2. Create/link the project with `npx eas-cli@latest init`. Copy its real project
   UUID into `EXPO_PUBLIC_EAS_PROJECT_ID` in `.env.local` and the EAS environment
   used for your build. If EAS cannot edit the dynamic config automatically,
   set the UUID yourself; `app.config.js` reads it or `app.json`'s `extra.eas.projectId`.
3. Configure Android FCM v1 and iOS APNs credentials in EAS. For Android, provide
   the real `google-services.json` as the `GOOGLE_SERVICES_JSON` EAS file environment
   variable, or set that variable to its local file path for local builds.
4. Deploy the website and backend changes in this repository. The website bridge
   must be present on the same origin loaded in the WebView.
5. Build/install on a physical phone:

```powershell
npx eas-cli@latest build --profile development --platform android
npx expo start --dev-client
# Internal Android APK:
npx eas-cli@latest build --profile preview --platform android
# Store builds:
npx eas-cli@latest build --profile production --platform all
```

The configured identifiers are `in.fuseon.synapse` (both platforms). Change them
before the first store release if you already own a different application ID.
No project ID, signing credentials, or push token is fabricated. Remote push
notifications require an installed development/preview/production build and real
push credentials; Expo Go is not the remote-push test environment.

See [Expo push setup](https://docs.expo.dev/push-notifications/push-notifications-setup/)
and [EAS builds](https://docs.expo.dev/build/introduction/).

## Offline behavior

The app saves the last readable page as an inert HTML document in its private
document directory. Styles are copied inline; up to 24 successfully loaded images
are cached locally (2 MB per image, 8 MB total). Text is saved before downloads,
so losing connectivity during an image download still leaves readable content.

With no internet, including after a cold start, the app opens the saved file and
shows a native offline banner with its saved time. It is read only: posting,
registration, sending messages, and navigation require a connection. Reconnecting
restores the online WebView. A first launch without previously saved content shows
a native reconnect screen.

The offline copy excludes scripts, form fields, videos, embeds and sensitive
account/admin pages. JavaScript is disabled in the offline WebView. Local copies
are cleared on logout/account changes. Images blocked by a CDN, missing size
headers, oversized media and external fonts/background images may be omitted;
the text remains available.

## Push flow

The native bell requests permission when the user chooses to enable alerts.
Existing permission is restored after sign-in. Expo push tokens are registered
through the website's authenticated `/api/v1/notifications/devices` endpoint;
access/refresh tokens never cross the native bridge or enter the page cache.

The backend queues notifications generated by team/social actions and chat
messages. Its MongoDB-backed worker sends to Expo, retries transient failures,
checks delivery receipts after 15 minutes, and removes unregistered devices.
User notification preferences, device token rotation, logout and account changes
are respected. Receipt success means acceptance by FCM/APNs, not proof of display
on a phone. `EXPO_ACCESS_TOKEN` may be set only on the backend if enhanced Expo
push security is enabled.

Email/password sessions use the existing website flow. Browser-based OAuth
providers must be verified in an installed app before release; external browser
popups do not automatically share the WebView's cookie session.

## Verification

```powershell
npm test
npm run typecheck
npm run lint
npx expo-doctor
npx expo export --platform all --output-dir dist
```

From the repository root, test authenticated push registration, MongoDB queues,
token rotation, preferences, retries and receipts using mocked Expo transport:

```powershell
$env:RUN_PUSH_INTEGRATION = '1'
node --test synapse-backend/services/pushService.test.js synapse-backend/services/pushService.integration.test.js src/lib/nativeBridge.test.js
Remove-Item Env:RUN_PUSH_INTEGRATION
```

That test creates/removes its own `synapse_push_qa_*` local MongoDB database and
never sends a notification to a real device. It requires MongoDB on port 27017.

Before submitting a store build, test on Android and iOS:

- Load a feed/event, wait for its images, enable airplane mode, then force-close
  and relaunch. Verify the saved content, timestamp and offline banner.
- Reconnect, pull to refresh, use Android back, and open an external event link.
- Log out and log in as another user; previous private content must not appear.
- Enable alerts and trigger a team invite/message from a second account. Check
  foreground, background, terminated-app delivery and notification tap routing.
- Revoke permission, rotate/reinstall a device, and verify device registration
  and the queue's delivery receipts.
- Verify email/password, CAPTCHA and any OAuth providers in the installed build.

The implementation provides native capabilities that can be demonstrated during
review. Store approval still depends on the finished app and review requirements.
